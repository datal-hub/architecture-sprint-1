# Спринт 1. Практическая работа 1.

## Пункт 1. Module Federation vs Single SPA

Я принял решение использовать подход через Module Federation по следующим причинам:
- уже был опыт работы с этим подходом в рамках лабораторной работы
- Module Federation позволяет переиспользовать код между микрофронтендами, мы сможем это использовать при работе с контекстом и верификацией пользователя
- у нас разные части приложения (профиль, галерея) могут иметь разное время загрузки, соответственно в случае использования Module Federation мы получим более быструю загрузку стартовой страницы

## Пункт 2. Разделение на микрофронтенды

Я разделил проект на следующие логические микрофронтенды:
- Модуль аутентификации (auth)
  - компонент аутентификация (Login)
  - компонент регистрации (Register)
  - функция проверки токена (CheckToken)
- Модуль профиля (profile)
  - компонент редактирования аватара (EditAvatarPopup)
  - компонент редактирования информации о пользователе (EditProfilePopup)
  - компонент добавления нового места (AddPlacePopup)
  - компонент общей формы (PopupWithForm)
  - компонент профиля (Profile)

- Модуль галереи (gallery)
  - компонент карточки (Card)
    - просмотр
    - удаление
    - лайки
  - компонент ленты фотографий (Gallery)
  - компонент просмотра фотографии карточки (ImagePopup)

Также следует отдельно выделить служебные микрофронтенды:
- host - собирает все микрофронты в общее приложение
- context - предоставляет доступ к информации о пользователе тем микрофронтам, где это требуется

### Обоснование разделения

Такое разделение мотивируется тем, чтобы разделить разные части приложение на отдельные логические блоки с которыми разные команды смогут работать независимо.

Так модуль аутентификации представляет отдельный микрофронт, потому что он обособлен от основной бизнес-логики и по сути связан только с хостом, он имеет свою отдельную API и команда сможет работать с ним независимо от других мирокрофронтов.

Модуль профиля собирает в себе всю логику работы с данными пользователя в том числе добавление новых фотографий и логически отделен от галерии, которая может содержать в себе данные других пользователей, где важно учитывать контекст.

Ну и наконец галерея выделена в отдельный компонент, который потенциально будет наиболее нагруженным из-за количества данных, которые необходимо отрисовывать и который мы в перспективе захотим оптимизировать.

## Пункт 3. Запуск

Для запуска необходимо выполнить следующие шаги:
- из корня проекта выполнить команду `docker compose up --build -d`
- затем последовательно выполнить запуск микрофронтов:
  - /frontend/microfrontend/auth 
    - npm install
    - npm start
  - /frontend/microfrontend/profile 
    - npm install 
    - npm start
  - /frontend/microfrontend/gallery 
    - npm install 
    - npm start
  - /frontend/microfrontend/host
    - npm install
    - npm start
- после этого приложение станет доступно по адресу http://localhost:8080
